### 400 时的原文

- `stash`：

  > 无效请求：解析到的代理节点均无法由所选输出目标表示。

## 三、对照实验：400 的那几个格式本身没坏

上面第 16–20 行只说明「**这份订阅里没有 ss / ssr / trojan 节点**」，不代表格式坏了。

拿一份含对应协议的公开订阅（`mheidari98/.proxy`）喂给同一个后端：

| 格式 | 结果 |
| --- | --- |
| `ss` | 200，**3656** 条 URI |
| `ssr` | 200，**767** 条 URI |
| `trojan` | 200，**2091** 条 URI |
| `ssd` / `sssub` | 200，返回 872 KB / 1.46 MB 正文 |

**所以 `ss` / `ssr` / `trojan` 属于「协议过滤型」格式 —— 手里有什么协议就出什么，没有就报错。建议保留。**

## 四、两个跨格式的共性问题

### 1. `quanx` 没有生成远程资源段

SCE 的 README 把 `quanx` 和 `surge` / `loon` / `surfboard` / `stash` 一起归入「**客户端原生远程资源**」，按设计应该在 `[server_remote]` 里写上订阅地址、让 Quantumult X 自己去拉。

实测结果：

| 来源 | `[server_remote]` | `[server_local]` |
| --- | --- | --- |
| 本站 feed | **0 条** | 2 条 |
| 公开订阅 freefq | **0 条** | 7 条 |

`quanx` 的输出里**从头到尾没有出现订阅地址**，只有后端内联的那几条。也就是说它走的是「后端转换」而不是「远程资源」，节点数完全受后端表达能力限制 —— 本订阅只出 2 个。

### 2. 有一类节点所有格式都装不下

这份订阅里有 3 个节点用的是 **xhttp 传输**（`type=xhttp`，其中 2 个还叠加 `security=reality`）：

```
SG.56idc-vl-xhttp-reality-enc
SG.56idc-Vless-xhttp-tls-UDP
JP.56idc-vl-xhttp-reality-enc
```

`singbox` 明确丢掉了这 3 个（15 → 12）。只有 `shadowrocket` 和 `vless` 这种 URI 直通的格式能把它们原样带出去。

## 五、这份订阅为什么这么多格式出不全

`bighead` 的 15 个节点构成：

| 协议 | 数量 | 备注 |
| --- | --- | --- |
| vless | 12 | 其中 **3 个是 xhttp 传输**，**6 个用后量子加密** `encryption=mlkem768x25519plus.native.0rtt.*` |
| vmess | 1 | 无名称 |
| hysteria2 | 2 | |

- **6 个后量子加密的 vless**：`v2rayn` / `v2rayng` 装不下（丢 6 个）
- **3 个 xhttp 节点**：`singbox` 装不下
- **12 个 vless + 2 个 hysteria2**：`quan` / `mellow` 只认 vmess，所以各只剩 1 个
- **15 个全部**：`surge` 的 `list=true` 模式直接 400 —— 后端认为一个都表达不了，于是退回远程资源模式

换句话说：**这份订阅的节点太新**，越老的客户端格式越吃不下。

## 七、备注

- 本文所有「内联节点」都是解析正文数出来的，不是看 HTTP 状态码 —— 后端出错时也会返回 200 带一段纯文本报错。
- `surge` / `surfboard` / `loon` 的「客户端实得」标了**待实测**：这三个是远程资源模式，转换结果里本来就不放节点，需要拿真机（或对应客户端）拉一次才知道那份 base64 的 v2ray 列表它们认不认。这条链路本地验证不了。
- 测试过程中后端对上游订阅的抓取出现过偶发 5xx / 空正文，脚本已带重试；`stash` 的 400 在重试后仍稳定复现。
